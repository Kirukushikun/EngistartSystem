1 · The contract (what every system implementing this must honor)

Ground rule: this feature is optional. The system must work perfectly with no hub connection at all — that's the normal state, not a degraded one. Login is never touched by the hub, under any circumstance. If the hub is down, unreachable, or was never enrolled, the rest of User Management behaves exactly as it always did.

What the hub actually is

One central list of people and their org role(s). Nothing more. The vocabulary is fixed to four values — manager, division_head, vp, user — and a person can hold more than one at once (["division_head","manager"] is a valid single entry, not two records). The hub doesn't know Engistart's role enum, module codes, or permission names. It says "Maria is a division head, and also a manager" and stops. What that means inside Engistart is Engistart's business — that translation is exactly what §2 below documents.

What a sync receives

    {
      "user_id": 87,
      "name": "Juan Cruz",
      "email": "j.cruz@example.org",
      "farm": "Farm B",
      "department": "Operations",
      "position": null,
      "roles": ["manager"],
      "active": true
    }
  ]
}
  • user_id is the same numeric ID Engistart's users table already keys on — already decrypted, nothing to decrypt on receipt.
  • roles is always an array. A mapping step that reads roles[0] and stops is a bug — it must iterate the whole array.
  • active: false is the revoke signal, not something to filter out on arrival.
  • An unknown role string means "skip that string, warn" — never "crash" and never "drop the whole person" if at least one of their other roles is recognized.
  • farm / department / position are display-only, with no bearing on access. All three can be null and often are — never gate anything on them, never let a null one break a sync.

RequirementWhy
A source column (hub / manual)Sync only ever touches rows it owns. This one column is what guarantees a hand-added account is never modified or deleted by a sync.

2 · What Engistart specifically decided

The contract above is deliberately generic. These four calls were this project's to make.

2.1 — The role map

Hub roleEngistart roleReasoning
division_headdivision_headDirect match
vpvp_gen_servicesThe only VP-level role Engistart has
managerfarm_managerClosest operational equivalent
userunmapped, deliberatelyA plain hub user with no management role gets no Engistart login at all

dh_gen_services, ed_manager, it_admin, engineer, guest have no hub equivalent. Those roles stay permanently source = manual — the hub never creates, touches, or revokes them, because it never mentions them.

2.2 — Multiple hub roles on one person, who wins

Engistart's users.role is a single enum column (not a JSON/bitmask access set), so the contract's "decide up front how they combine" resolves to highest-privilege wins: vp_gen_services > division_head > farm_manager. That ordering is a private const PRIORITY inside HubRoleResolver — not in config/hub.php — because the contract is explicit that this decision belongs in the code that reads the mapping table, not the table itself. config/hub.php stays a flat, no-logic lookup.

2.3 — Farm / department / position: display-only, or stored?

The contract calls these optional and display-only. Engistart's call: store all three on source = hub rows, overwritten on every sync.

Consequence accepted deliberately: users.farm also seeds the default farm_name on a new Farm Manager request (NewRequestPage.php), so a hub sync can silently change what a farm manager's next submission defaults to. position didn't exist on users before this integration — it was added specifically for it.

2.4 — The actual wire protocol

The contract explicitly defers this to the hub repo's own docs/api.md. The exact shape implemented and independently verified against real source (§5):

  • Base URL: https://accesshub.bfcgroup.ph — /login is the human page; the API root has no path suffix.
  • POST /api/v1/enroll — body {code, project_key, environment} → {client_id, client_secret}. project_key is this project's own registration on the hub, set up by a human on the hub admin side — never a placeholder to invent.
  • GET /api/v1/grants — auth via two custom headers, X-Client-Id and X-Client-Secret (not x-api-key, not Authorization: Bearer).

What UsersPage itself gained

saveUser() and toggleAccess() were refactored to call UserAccessManager instead of writing users directly — this is what makes "no second write path" literally true, not just documented. Editing a hub-owned row through the ordinary panel flips it to source = manual (an intentional escape hatch: a manual edit is manual intent), while the plain enable/disable toggle does not flip source — a temporary disable isn't a claim of ownership.

5 · Behavior when things go wrong

Enrollment

Hub responseEngistart shows
200Stores client_id/client_secret, panel flips to the preview
404"the hub does not recognize this project key"
422"the code is wrong, expired, or already used"
429"rate-limiting enrollment attempts, wait a moment"
network failure"Could not reach the Access Hub to enroll"

No connection is ever partially created — any failure leaves hub_connections exactly as it was.

While connected

SituationShownlast_synced_at
Hub unreachable / times outGeneric error, "User Management is unaffected"untouched
401/403 (revoked/invalid)Dedicated message + a Reset connection button, not a retry promptuntouched
429 on the grants call"rate-limiting sync requests"untouched
Malformed response (people missing)Generic erroruntouched

"Reset connection" deletes the hub_connections row outright and drops the panel back to State 1 — the only way forward is enrolling again with a fresh code.

Two things this integration deliberately does not do

  • It never touches login. AuthController has no reference to the hub anywhere. Access Hub and BFC's Auth API (what users actually authenticate against) are two unrelated systems that happen to both be "external BFC APIs." The hub only ever decides what role a source = hub user has, never whether someone can log in.
  • It never overwrites anything an admin granted by hand. Every write path checks source === 'hub' before touching an existing row. A source = manual account — including every account for a role the hub doesn't know about — is invisible to the sync in every direction.

6 · Checklist & deploy runbook

Built & verified

  • source column added, existing rows default to manual
  • Role mapping config committed, flat, logic-free, keyed on the current 4 hub roles
  • Multiple-roles-per-person combine rule lives in HubRoleResolver, not the config
  • Farm / department / position shown in preview, tolerant of nulls, stored on hub rows (§2.3)
  • Connection row — client ID, encrypted secret, last_synced_at
  • Hub base URL in committed config, no secrets in .env
  • Enrollment card on first sync, "Reset connection" available thereafter
  • Compare produces three groups: new, changed, local-only
  • Preview shown before any write, admin confirms per row
  • Apply reuses UserAccessManager — no second write path
  • Sync never modifies or deletes source = manual rows
  • User ID set explicitly on create, not mass-assigned
  • last_synced_at stamped on fetch only, amber past 30 days
  • Every hub call has connect and read timeouts
  • Panel verified working with the hub switched off entirely
  • 44 automated tests — HubSyncTest.php (resolver/compare/apply/lifecycle) + HubClientTest.php (real HTTP layer via Http::fake())

Deploying this for real

  1. Get this project's project_key and a one-time enrollment code from whoever administers accesshub.bfcgroup.ph.
  2. Set HUB_BASE_URL and HUB_PROJECT_KEY in the environment's .env.
  3. As IT Admin: User Management → "Sync from hub" → paste the code → Connect.
  4. Review the New/Changed lists, tick what's right, Apply.
  5. From then on, "Refresh preview" + "Apply selected" is the whole workflow. Watch the last-synced line — past 30 days, it turns amber on its own.
